# 07｜给 KylinNote 改造用的设计工作简报

[返回目录](README.md) · [布局与实现](01-layout-and-implementation.md) · [菜单矩阵](04-menus.md)

> 本章是**我们的设计建议，不是滴答产品事实，也不是已经实施的改造**。本轮未修改或运行KylinNote应用源码，没有提交/推送。沿用同仓上一份研究中对提交 `b6c19f3` 的静态映射，后续实施仍要重新核对源码与需求。

## 1. 推荐结论

**模仿它的组织和操作逻辑，不机械复制全部产品。** 先保留Qt离线任务＋桌面便签定位，把现有三栏做得清晰、一致、可发现；再按真实需求决定是否扩展任务模型和高级视图。

成熟产品提供的是一个高质量参考，而不是“每个按钮位置都对本项目最优”的证明。其云协作、会员、AI、习惯和大量历史兼容入口有自身背景，我们不必为了像它而同时增加。

## 2. 第一阶段应该接近的工作台

```text
[全局/应用入口] [组织导航] [当前视图：标题、排序、更多]
                         [快速添加]
                         [任务行：完成框 | 标题 | 属性]
                                          [详情：完成/日期/优先级]
                                          [标题、正文、子项]
                                          [归属 | 格式/附件/更多]
```

- 最左功能栏只有多个实际工作模块时才值得独立占50px；单一任务项目可先把全局入口保留在现有导航区。
- 智能视图、真实分组、标签、历史/回收站分区。不要只靠颜色让用户猜对象类型。
- 列表头部只放视图级动作；任务属性放行内/详情；备份和自启放设置或应用菜单。
- 保留固定快速添加入口，明确当前视图的新任务究竟落到哪里。
- 长正文、子项独立滚动，高频属性与底部命令不被长内容挤走。

## 3. 不要把相似名称当成同一业务

| 滴答里的概念 | KylinNote需要单独决定的问题 |
|---|---|
| 文件夹→清单→分组 | 现有单层TaskGroup能否表达？不应仅把侧栏缩进画出来 |
| 任务置顶 | 不等于“贴到桌面”，也不等于便签窗口置顶或z-order |
| 高/中/低/无四档优先级 | 现有模型三档如何映射、旧数据怎样迁移？不能只多画一面旗 |
| 子任务 | 现有ChecklistItem的文字/完成状态不等于有独立日期、附件、身份的任务树 |
| 看板/时间线 | 是同一任务数据的显示视图，不应复制一套任务数据库 |
| 转换为笔记/任务 | 正文、附件、日期、子项和完成状态的保留契约是什么？ |
| 放弃、完成、删除 | 三种语义不同；恢复、归档、永久删除也需分别定义 |
| 创建副本 | 是否复制附件、提醒、子项、便签属性？不得比当前能力承诺更多 |
| 提醒 | 不因界面像滴答就获得关机唤醒、跨设备或云端提醒能力 |
| 视图跨设备同步 | 当前离线项目不存在对应云同步契约，不保留无效开关 |

现有能力和静态路径的详细依据见[此前KylinNote源码映射](../ticktick-windows-6.3.3/08-kylinnote-adaptation.md)。那篇对Windows滴答的推测不能替代本册Web实测，但其本项目源码映射可作为同提交的起点。

## 4. 本项目改动入口（实施前复核）

| 区域 | 现有文件 | 本轮建议 |
|---|---|---|
| 主工作台与导航 | [TaskPanel.cpp](../../../src/ui/TaskPanel.cpp) | 组织层级、视图级动作、快速添加、选择状态 |
| 列表行与角色 | [TaskDelegate.cpp](../../../src/ui/TaskDelegate.cpp)、[TaskListModel.cpp](../../../src/ui/TaskListModel.cpp) | 标题与元信息分层；hover/selected/focus与完成框命中区 |
| 详情 | [TaskDetailWidget.cpp](../../../src/ui/TaskDetailWidget.cpp) | 高频属性上移，正文与子项优先，低频命令统一收纳 |
| 设计令牌 | [AppStyle.cpp](../../../src/ui/AppStyle.cpp) | 字体、间距、颜色、圆角、行高和图标热区统一 |
| 桌面便签 | [NoteWidget.cpp](../../../src/ui/NoteWidget.cpp)、[TitleBar.cpp](../../../src/ui/TitleBar.cpp) | 保留轻量投影；关闭便签不误变成删除任务 |
| 全局与提醒 | [TrayController.cpp](../../../src/app/TrayController.cpp)、[ReminderPopup.cpp](../../../src/ui/ReminderPopup.cpp) | 与主窗共享命令语义，明确稍后/知道了/完成的差别 |

不建议为得到类似外观引入整个浏览器前端或复制React发布bundle。Qt可以表达多栏、统一QAction、弹层、滚动与状态样式；技术栈变化应另立需求，而不是当皮肤改造的前提。

## 5. 推荐实施顺序

### P0：不扩模型，先统一交互

1. 清理顶部功能堆叠；把视图操作、对象操作和应用设置分开。
2. 统一设计令牌、任务行信息层级、悬停/选中/键盘焦点。
3. 详情优先显示完成、日期、优先级；便签颜色/层位进入低频区。
4. 右键、按钮、快捷键共用命令执行入口，避免同一动作的保存前置和错误处理不同。
5. 明确视图切换、保存失败、删除后选择落点；不丢草稿和滚动位置。

**验收**：旧数据可读、原业务不回退；所有按钮有可发现名称；窄窗仍有明确主区；不以像素相似替代可用性。

### P1：用已有字段增强效率

- 快速添加日期/分组/优先级快捷入口；自然语言解析未实现时不展示同等承诺。
- 标签基础聚合、日期分段、搜索空态与筛选提示。
- 按对象和状态生成菜单：普通、完成、回收站至少分开；危险动作有确认/恢复路径。
- 详情更多与右键共享核心动作，但不要求菜单集合相同。
- 让图标有工具提示及可访问名称；不要复制现场观察到的无名称按钮问题。

### P2：经需求确认后扩展模型

真正子任务、文件夹层级、手动顺序、四档优先级、多提醒/复杂重复、看板和时间线、保存的高级过滤条件。每项先定义数据、迁移、事务与备份契约，再设计对应入口。

四象限、习惯、专注、AI、云协作不是“换一下UI”即可附赠的能力；可以不做，也可以拆成独立版本。

## 6. 设计令牌如何使用本次测量

- 50px功能条、36px导航行、40px任务行、48px详情工具栏，是滴答特定环境的参考；不是必须一模一样的目标值。
- 本项目应按中文密度、系统缩放、键盘/鼠标热区、Qt字体测量再定自己的值。
- 用“背景/正文/次级字/边界/主题/过期/优先级/危险”语义令牌，而不是散落的颜色常量。
- 把“选择态”“悬停态”“焦点态”“禁用态”分开；不要仅凭alpha变淡判断事件已经禁用。
- 折叠、覆盖详情、设置小窗适配应是明确规则，不能靠绝对坐标应付。

## 7. 以后真正开工时的回归清单

本次**没有执行这些测试**：

- [ ] 新建落点、中文输入法、长标题、多标签、无结果与清空搜索。
- [ ] 快速连续切换任务时草稿保存；保存失败后的重试、焦点和选择保持。
- [ ] 完成框、详情、右键、快捷键对同一任务走一致保存/状态链。
- [ ] 右键命中目标与已有多选范围；空白区、多选、完成、回收站菜单。
- [ ] 重复任务、防抖期间完成、跨午夜、时区、月末和提醒去重。
- [ ] 关闭便签不删任务；主面板布局不覆盖便签几何/层位。
- [ ] 附件、复制、备份往返、重复导入、旧数据迁移和异常回滚。
- [ ] 不同窗口与125%/150%缩放、键盘焦点、屏幕阅读器命名与对比度。
- [ ] 所有后续涉及浏览器前端的测试以 `C:/Chrome78` Chromium78为兼容起点；Qt界面另以QtTest及Windows/麒麟目标机验证。
